Three hierarchies for a visit in the journey

The built row prints every field of every visit: keyword, cost, interaction, bot probability, VPN, network, form, conversion, location, device. Four visits in, the reader has read forty facts and still does not know which visit mattered. Each option below shows the same three visits from golden case 7: a quiet visit (1), a visit where something changed (2), and the decision visit (5), expanded. The rule shared by all three: a collapsed row shows only what a person needs to place the visit in the story; everything else is one disclosure away, never gone.

1 · what changed

Source, one line of engagement, and only what changed

Three lines when collapsed: the visit label and time; where it came from; a single engagement line (time on page, scroll, outcome). Below that, only facts that differ from the previous visit or are unusual, as tags: a new location, a new device, an undeliverable email, a conversion. Defaults such as "VPN: No" and "Form: Not submitted" never appear collapsed. The disclosure opens the full record grouped by the brief's four categories.

Rationale

A journey is read as change over time. A field that is the same on every visit carries no information on any of them, so it is shown once (in the header) and only its changes appear on the rows. The engagement line stays because it is the one number the customer compares visit to visit, and the brief's success test asks which visits contributed.

Solves
  • Collapsed rows are three lines; a 14-visit journey fits on a screen
  • Changed facts stand out because nothing else competes
  • Absence is honest: a visit with no tags is a visit where nothing changed, not a visit with missing data
Costs
  • "Changed since the previous visit" needs computing per visit (new data work)
  • The first visit has no previous, so its tags are "unusual" rather than "changed", a slightly different rule
  • The engagement line hides bot probability, which some readers will look for on the row

2 · signal first

The visit as its contribution to the verdict

The collapsed row leads with the signals this visit contributed to the decision, using the same labels the table and the evidence list use ("Low interaction", "Same keyword", "Email: Invalid"), followed by one muted line of time and source. Nothing numeric is shown collapsed. A visit that contributed nothing says so with a dashed "No signals" tag. The disclosure opens the full record and, above it, the evidence sentences this visit supports, so the row and the evidence list are the same facts from two directions.

Rationale

The customer's question is not "what happened on this visit" but "why did this visit count". Leading with contribution answers that directly and gives the journey the same vocabulary as the table row that opened it and the evidence list beside it, so the three surfaces reinforce one another instead of describing the same visit three ways.

Solves
  • Quiet visits read as quiet at a glance; the decision visit is visibly the heaviest row before it is opened
  • One vocabulary across table, evidence and journey (D10a)
  • The block marker follows naturally: the visit whose signals crossed the line sits directly above it
Costs
  • Engagement numbers are hidden collapsed, so comparing visit to visit needs the disclosure
  • The engine already attributes evidence to visits; the row needs that attribution exposed per visit, and a "changed" fact still needs computing for the identity tags
  • For a Not blocked visitor most rows carry only mitigating tags, which is correct but visually thin

3 · ledger

One line per visit, the decision visit opened in place

Each visit is a single row: number, time, what happened in a few words with the source beneath, up to two signal tags right-aligned, and a chevron. The decision visit is tinted and opened in place, showing the same grouped record as option 1. The block marker follows it. This is the densest form: a 14-visit journey is 14 lines.

Rationale

The journey's job is sequence. A ledger makes sequence the strongest thing on the page: the eye runs down one column of times and one column of tags and finds the row where the tags turn red. It suits the long journeys in the data (up to 14 visits) and the customer who has read the summary and wants to confirm the pattern, not re-read it.

Solves
  • The whole journey is visible without scrolling, so "which visits contributed" is answered by the tag column alone
  • Scanning by time is fast: one column, one format
  • Density without noise: nothing numeric is shown collapsed
Costs
  • Loses the narrative line ("Landed on /pricing from ...") that makes a visit read like an event
  • Two tags fit on a line; a visit with four signals truncates to "+2"
  • Reads like a second table under the table, which the detail page was meant to escape; on a phone the columns must stack, losing the ledger's point

How to choose

  • Choose 1 if the journey should read as a story of change: what was different each time. It keeps the narrative line and the one number worth comparing. It is the closest to the recommended detail design.
  • Choose 2 if the journey should read as an argument: what each visit added to the verdict, in the words the table and the evidence list already use. It is the strongest fit for D10a's one vocabulary, at the price of hiding engagement numbers collapsed.
  • Choose 3 if long journeys and fast scanning matter more than narrative. It is the densest and the least like an explanation.
  • 1 and 2 combine cleanly: option 1's three lines with option 2's signal tags in place of the "changed" tags. That hybrid shows change and contribution on one row, at the cost of a fourth line.

Shared build work whichever is chosen: a per-visit "changed since the previous visit" fact for location and device, per-visit evidence attribution exposed from the engine (it already exists inside the evidence items), the four-category grouping of the full record, and the decision visit open by default with the block marker directly after it.
